# Panorama Reconstruct - WebGPU 版

`panorama_recon.py`（動画からのグローバル整列 + 時間的中央値による背景再構成）をブラウザ上で動かす移植版。
torch / CUDA を使わず、WebGPU の計算シェーダー（WGSL）だけで動作するため、配布物は静的ファイルのみ。
NVIDIA / AMD / Intel の GPU を問わず、WebGPU 対応ブラウザなら動く。

## 起動

ES モジュールを使うため `file://` では動かない。任意の静的サーバーで配信する。

```bash
cd web
python -m http.server 8765
# → http://127.0.0.1:8765/index.html
```

対応ブラウザ: Chrome / Edge 113+、Firefox 141+（Windows）、Safari 26+。
Linux の Chrome は WebGPU がフラグ付きの場合がある。

WebGPU の利用可否はページ表示時に判定し、見出し直下に表示する（利用可能なら GPU 名、不可なら赤いバナーで原因と対処。
「実行」は無効化される）。対応ブラウザでも次の場合は使えない:

- Chrome / Edge で「設定 → システム → グラフィック アクセラレーションが使用可能な場合は使用する」が OFF
  （ON にしてブラウザを再起動。`chrome://gpu` で WebGPU の状態を確認できる）
- `http://` で localhost 以外のホスト名から開いている（WebGPU はセキュアコンテキスト限定。`127.0.0.1` / `localhost` か `https://` で開く）
- リモートデスクトップ / 仮想マシンなど GPU が無い環境、ドライバがブロックリストに載っている場合

## メモリ上限（memory limit）

全フレームを GPU バッファに常駐させるため、1080p で約 9 MB / フレーム（フレーム 8 MB + 前処理 1 MB）を消費する。
2000 フレームなら約 20 GB。VRAM を超えた分は OS がメインメモリに退避させるので、メインメモリが足りないとブラウザごと
クラッシュする（実測: 1080p 2130 フレームは 64 GB の PC で完走、32 GB の PC でクラッシュ）。空きメモリや VRAM 量を取得する
Web API は無いため、上限は利用者が「memory limit (GB)」欄で設定する（既定 8 GB、localStorage に保存、0 で無制限）。
目安はディスクリート GPU ならメインメモリの 1/2 以下。オンボード GPU（共有メモリ）は OS がプロセスに割り当てる GPU メモリ予算が
メインメモリよりずっと小さいので 4〜6 GB から始める（実測: メインメモリ 32 GB / 共有 3 GB の PC で 10 GB 設定は 7 GB 未満で失敗）。
「上限を確認」ボタンは、動画を読み込まずに設定値まで 512 MB ずつ実際にバッファを確保して確かめる。確保できなければ上限を
確保できた量の 80% に下げて保存する。ブロックごとの確保時間もログに出す（2026-09-14 追加）: 確保に成功しても途中から急に遅くなる
場合は仮想メモリ（ページファイル）に退避しているので、遅くなり始めた量より下に上限を設定した方が処理は速い。

- 実行時、フレーム数と解像度が確定した時点（抽出前）で GPU バッファ総量を見積もり、ログに `[memory] 推定 ...` と出す。
  上限を超える場合は抽出前に中止し、収まるフレーム数と対処（fps / max frames / input scale / Trim）を表示する
- 見積もりに含まれないキャンバス出力等で超えた場合も、確保時に上限を超えた時点で例外にして中止する（render 開始時にまとめて判定）
- WebGPU が out-of-memory を報告した場合も次の同期点で中止する
- Dawn（Chrome の WebGPU）内部の確保（フレーム転送のステージング等）で D3D12 が out-of-memory を返すと、通常のエラーではなく
  デバイス喪失（`[device] LOST ... CreateCommittedResource ... OutOfMemory`）になる。この場合はログに
  「GPU メモリ不足で GPU デバイスが失われました」と出して中止し、次の実行時にデバイスを作り直す（ページ再読み込み不要）。
  直後に出る `seek error` はデバイス喪失の結果であって原因ではない
- 完了時に `GPU buffer peak` を表示する。sample.mp4（135 フレーム）は推定 2.28 GB に対して実測ピーク 2.43 GB
- 上限に収まらない場合は自動でストリーミングモード（下記）になる。それでも足りなければ `input scale` 0.5 でフレームあたり 1/4、
  `fps` を半分で 1/2、Trim で範囲を絞る

## ストリーミングモード（メモリ節約の自動分割）

全フレームを常駐させると上限を超える場合、フレームを必要なときだけ動画から読み直す方式に自動で切り替わる
（ログに `[memory] ストリーミングモード: フレームキャッシュ N frames` と出る）。動画を区間に分けて別々に合成する方式ではなく、
位置合わせは全フレームで一括して解くので、分割点やのりしろを決める必要はなく、結果も常駐時と同一になる
（sample.mp4 / sample2_jigzag.mp4 / 90° 回転した sample.mp4 で、位置と 4 種の出力画像がバイト単位で一致することを確認済み）。

- フレームは `frames.js` の `FrameStore` が LRU で常駐させる（上限 = memory limit から常駐データと作業領域を引いた残り）。
  前処理で決まるマスク（alpha）は 1 bit/画素にパックして保持し、読み直したフレームに復元する
- 前処理はフレーム順のパイプライン（静止検出 → 時間方向クロージング → 縮小レベル生成）で、k±span と k±close の窓だけ常駐していれば足りる
- 精密位置合わせのペアは (i, j) 昇順に処理し、読み直しを最小にする。粗探索データとレベルキャッシュは位置合わせ後に解放する
- 合成はキャンバスを帯に分け（動きが縦なら行帯、横なら列帯）、帯を覆うフレームだけを順に投影する。隣り合う帯はほぼ同じフレームを使うので
  キャッシュが「1 帯を覆うフレーム数」以上あれば読み直しは 1 回で済む。足りない場合はフレームを等間隔に間引く（ログに警告。
  標本数が減るだけで位置は変わらない。先頭 / 末尾 / アンカーのフレームは常に使う）
- 全フレームぶん常駐するデータは 1080p で約 1.9 MB/frame（1/4 レベル 1 MB、鮮明度 0.5 MB、マスク 0.26 MB）。2000 フレームで約 4 GB
  なので、上限がそれ以下なら fps か input scale を下げる必要がある（ログの `[memory]` 行に扱えるフレーム数が出る）
- コスト: 動画のシーク抽出が位置合わせと合成で約 2 回になる（`[frames] decoded 281 (2.08x of 135 frames)` のように表示）。
  sample.mp4 では総時間 64 s → 69 s。実例: 1080p 91 s の動画（フレーム 27-2157 をトリム、10 fps で 889 フレーム、常駐なら 9.2 GB）を
  上限 4 GB で実行し、ピーク 3.34 GB・644 s で完走（前処理 114 s、粗探索 77 s、精密 333 s、合成 116 s。デコード 3.0 回/フレーム）

## 使い方

1. 動画ファイル 1 本、またはフレーム画像を複数選択する（名前の自然順にソート）。ページ上にドロップしてもよい。
2. 必要なら「パラメータ」を開いて調整する（動画の `fps` はズーム動画なら 30 を推奨。詳細は CLAUDE.md の注記参照）。
3. 「実行」。ログに Python 版と同じ形式の統計が出る。完了するとタブに結果画像が並ぶ。
4. 「PNG 保存」で表示中の画像を、`positions.csv` / `pairs.csv` ボタンで位置推定結果を保存する。
   保存名は入力ファイル名（拡張子なし）を接頭辞にした `sample_recon_median.png` のような形になる。

パラメータ名は Python 版の CLI オプションと対応している（`--static-span` → `span` など）。
Web 版だけの項目:

- `input scale`: 読み込み時にフレームを縮小する（GPU メモリと速度の調整用）。
- `stack budget MB`: 合成時のサンプルスタックの上限。帯域高さ（`band`）はこれに収まるよう自動で決まる。
- `level cache MB`: Gauss-Newton 用のフル解像度レベル画像の LRU キャッシュ上限。
- `text rects` / `text halo`: 画面内を動くテロップ（ティッカー等）の帯を `x,y,w,h` で指定する。矩形内は静止条件なしで
  勾配の高い画素を文字とみなしてマスクし、`text halo` px だけ広げる。動くテロップは静止検出では取れないため必須。
- `halo`: 静止エッジの周囲 N px 以内で静止している画素もマスクに含める。テロップ文字のグロー（白いにじみ）は平坦で
  勾配が小さく静止検出をすり抜けるが、これで拾える。副作用として静止エッジ周辺の平坦部が余分にマスクされる。
- `close`: 前後 N フレーム（両側）でマスクされている画素はそのフレームでもマスクする。テロップ上を横切る光沢アニメで
  一瞬だけ静止判定が外れるのを防ぐ。
- `hole fill` / `min clean`: 幾何的には覆われているのにクリーン標本が無い画素（テロップが常に載っていた場所。キャンバスの
  両端に出やすい）と、クリーン標本が「件数未満かつ被覆の % 未満」の画素を、周囲から push-pull 補間で埋める（`inpaint`）
  かぼかした値で置き換える（`blur`）。`none` で無効。埋めた領域は本来の細部が失われる。
- `exposure`（2026-09-16 追加、Python 版 `--exposure`）: フレーム間の明るさの違い（露出・フェード・プレイヤーの上下グラデーション）を
  重なりから推定して合成前に補正する。`auto` は画像列では on、動画では off。モデルはフレームごとのゲインとオフセット（チャンネル別）＋
  全フレーム共通の加算プロファイル（`profile`、画像端に密な節点の折れ線、x と y）。位置合わせ済みペアの重なりを 32 px ブロックに分け、
  クリーン画素の平均の差を IRLS で解く。ログの `[exposure] 重なりの差（中央値）4.60 → 1.41 階調` が補正前後の一致度。`exposure.csv`
  ボタンでフレームごとの値とプロファイルを保存できる。
- `local`（既定 6）: フレームごとの局所オフセット場（長辺 N セルの双一次格子）。湯気や光の当たり方など位置によって違う明るさの差を
  重なりから推定して補正する（`sample_image3/` で必要）。0 で無効。フレーム数 > 100 では自動的に無効。
- 「ノイズ除去」ボタン（結果表示の横、しきい値入力付き）: 表示中の画像に à trous（starlet）ウェーブレットのノイズ除去を掛けて
  `<名前>_dn` タブに出す（`denoise.js`、Python 版 `wavelet_denoise.py` と同じ処理）。非間引きの B3 スプライン変換で詳細係数を
  軟しきい値で縮小するので、平坦な塗りと輪郭線が主体のアニメ画像で輪郭を残して粒状ノイズや JPEG のモスキートだけを落とせる。
  しきい値は最細レベルの階調（目安 6〜12）。スティッチとは独立した後処理で、何度でも別のしきい値で掛け直せる。
- `feather px`（空欄 = auto）: 「blend」タブ。各フレームの端から N px でなだらかに重みを落として重ね合わせ、露出補正後に残る差を
  境界でぼかす。auto は画像列ではフレーム短辺の 1/4、動画では出力しない。0 で出力しない。

## 静止画（スクリーンショット）の連結

サイズの異なる画像を混ぜて選んでも動く（2026-09-16）。以前は先頭画像のサイズに引き伸ばしていたため縦横比が崩れて位置合わせに失敗した。
現在は最大サイズのキャンバスに左上詰めで置き、右・下は端の画素を複製して埋める。複製領域は位置合わせと合成の両方から除外され、
キャンバスの範囲にも含まれない（ログに `[load] サイズの異なる画像を ... に揃えました` と出る）。サイズは PNG / JPEG のヘッダから読むので
事前のデコードは不要。`sample_image1/`（1920x939〜1080 の 5 枚）で Python 版と 1 階調程度の差で一致する。

枚数が少ないと `pairs` の 2, 4 間隔のペアは重なりが無いが、滑らかな輪郭が偶然合って高い NCC が出ることがある。粗探索のグローバル解は
まず隣接ペアの連鎖だけで解き、それと矛盾する離れたペアは重みを 1/1000 にする（ログ `far pairs inconsistent with chain=N`）。
また 1/16 解像度の全探索では最大値だけでなく局所ピーク上位 4 個を 1/4 解像度で再評価して選ぶ（`sample_image2/` で必要だった。
`window.__dbgCoarse = true` で候補ごとのスコアをログに出す）。

## Trim / Crop パネル

動画を選ぶと「Trim / Crop」パネルが開く（画像列では出ない）。

- 開始/終了フレームのプレビューを並べて表示し、範囲バーの両端ハンドルをドラッグして大まかに指定、`-1` / `+1` で
  1 フレーム単位に微調整、数値欄に直接入力も可。フレームレートは `requestVideoFrameCallback` で実測し
  （取れないブラウザでは fps 欄の値）、`fps` 欄の既定値にも入れる。フレーム番号はブラウザのシーク精度の範囲での近似。
- 矩形モードを Crop / Ignore rect / Text rect から選び、プレビュー上をドラッグして描く。Crop は 1 個で、ハンドルで
  拡縮、内側ドラッグで移動、アスペクト比プリセットあり。Ignore / Text は複数描け、`Remove last` / `Clear` で消す。
- プレビュー上にカーソルを置くとルーペ（既定 4 倍、ホイールで 2 / 4 / 8 倍）がカーソルの脇に出て、周辺の拡大画像と
  矩形の辺、元動画座標を表示する。辺を画素単位で合わせるときに使う。
- 描いた矩形はあとから編集できる。現在のモードの矩形の内側を押すと選択（太線）して移動、選択中の矩形のハンドルで拡縮。
  空いた所から描くと新規追加。Ctrl（Mac は Cmd）を押しながらドラッグすると既存の矩形の上からでも新規追加。
  Delete / Backspace で選択中の矩形を削除（Crop モードならクロップ解除）。
- Ignore / Text 矩形はクロップ後の座標に変換して「パラメータ」の `ignore rects` / `text rects` 欄へ自動で書き込まれる。
- 実行時は開始〜終了フレームの時間範囲だけをクロップして抽出する（`start` / `duration` 欄より優先）。

## 動くキャラクターと細線（anchor frame / res tol）

キャラクターの髪や体がカット内で動く動画では、グローバル整列は背景に合うため、動く層の細線は多数決の中央値で
塗りつぶされる（sample3_zoom.mp4 の髪の毛がこれ。フレーム 2→3 で髪と肩が約 12 px 動いている）。対策:

- `anchor frame`（抽出後のフレーム番号）と `± window`: そのフレーム群が覆う範囲はそれらだけで合成し、動く層をその姿で確定させる。
  Trim / Crop パネルの「Anchor = start / end」でプレビュー中のフレームを指定できる。範囲の境界で姿勢が変わる場合は継ぎ目が出る
  （window を広げると継ぎ目は目立たなくなるが動きボケが戻る）。
- `res tol`（既定 1.25）: 画素ごとに最も細部を持つ標本の拡大率 × この値以内の標本だけで合成する。ズームで引きのボケた標本が
  多数派になる場合の細線保護。0 で無効。
- 静止オーバーレイ検出はズーム中心付近の動かない細線をテロップと誤判定することがある。テロップの無い動画では検出を切るか、
  `span` を大きく（15 程度）する。

## Python 版との違い

| 項目 | Python 版 | Web 版 |
|---|---|---|
| 粗探索 | マスク付き NCC を FFT（Padfield）で全シフト評価 | 1/16 解像度で全シフトを総当たり → 1/4 解像度で ±12 px 窓を再探索（1 シフト = 1 ワークグループ） |
| スケール格子 | 1/4 解像度で `scale_step` 刻みを全探索 | 1/16 で 0.02 刻み → 1/4 で最良値の周辺を `scale_step` 刻み |
| 精密化（translation） | フル解像度 FFT NCC の窓探索 | フル解像度の総当たり窓探索（同じ範囲） |
| 精密化（scale / similarity） | Gauss-Newton（torch） | Gauss-Newton（WGSL）。MAD はヒストグラム近似、4x4 の正規方程式も GPU 上で解く |
| グローバル解 | numpy lstsq + IRLS | JS の正規方程式 + IRLS（同じ重み関数） |
| 合成 | torch nanmedian / nanquantile | ピクセルごとの基数選択（ニブル単位のヒストグラム）で中央値と分位点 |
| 動画デコード | OpenCV | `<video>` のシーク + canvas（ブラウザのコーデック依存） |
| 精度 | float32 | float32（WebGPU は f64 非対応） |

結果は Python 版とほぼ一致する。1 フレームあたりの移動量の差は平均 0.002 px、
1400 px スクロールした累積位置の差は最大 0.2 px、スケールの差は最大 7e-5（Web 版の抽出が 1 フレーム前にずれている分は
整列して比較）。

## メモリ

全フレームを RGBA8 で GPU に常駐させる（1080p で 8 MB / フレーム、136 フレームで約 1.1 GB）。
内蔵 GPU やメモリの少ない環境では `input scale` を 0.5 にするか、`fps` / `max frames` で枚数を減らす。

## ファイル構成

- `index.html` - UI
- `app.js` - フレーム読み込み（動画 / 画像）、実行フロー、出力
- `gpu.js` - WebGPU 共通基盤（カーネル、動的オフセット付き uniform、読み戻し）
- `shaders_img.js` - 前処理カーネル（グレー化、縮小、ぼかし、静止オーバーレイ検出、鮮明度）
- `shaders_align.js` - 総当たり NCC、argmax、Gauss-Newton
- `shaders_render.js` - ワープ、プリフィルタ、時間方向統計
- `recon.js` - 位置合わせの流れ（Python 版 `Reconstructor` に対応）
- `render.js` - 合成
- `solve.js` - CPU 側の最小二乗 / IRLS

これらは Python 版にも同名のオプション（`--text-rect`, `--static-halo`, `--static-close`, `--hole-fill` など）として移植済み。

## テロップの残骸が残るとき

1. 「overlay mask」タブで赤（マスク）が文字を覆っているか確認する。動くテロップは赤にならないので `text rects` で
   帯を指定する（フレーム座標。文字行の上下に余裕をもたせる）。
2. 白いにじみが残る場合は `halo` を大きくする（既定 12）。一瞬だけ文字が抜ける場合は `close` を使う（既定 3）。
3. キャンバス端の残骸は `hole fill` で埋まる。埋まらない場合は `min clean` の件数/％ を上げる。
4. `coverage` タブで暗い場所はクリーン標本が少ない場所。そこは埋められるか、少数の標本の中央値になる。

## 既知の注意点

- WGSL の `a || b` をワークグループバリアの前に置くと一部環境で誤コンパイルされたため、`gn_accum` では `max()` で判定している。
- 動画シークによるフレーム抽出は、ブラウザが最寄りのフレームに丸めるため、Python 版と 1 フレームずれることがある。
- キャンバスが `maxStorageBufferBindingSize` を超える場合はエラーになる。`canvas scale` を下げる。
